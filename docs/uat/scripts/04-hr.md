# 04 — HR & Payroll UAT script

Business acceptance scenarios for the HR & Payroll module: employee onboarding and org
structure, overtime approval and reconciliation, cash-advance decisions, attendance import,
the payroll run (calculate → review → approve), payslips, and statutory tax exports.

Audience: HR officer, payroll approver, Owner/GM. For environment bring-up see
`docs/testing/UI_TEST_PLAN.md` §Quickstart; engineer-level detail for the same screens lives
in `docs/testing/test-cases/04-hr.md`. Roles and their permission bundles are defined once in
`docs/uat/UAT_PLAN.md` — scenarios below refer to roles by name only.

**Coverage checklist**

- [ ] Orientation: HR workspace opens and the employee list reads correctly (UAT-HR-01)
- [ ] Golden workflow: org structure + onboard daily & monthly employees (UAT-HR-02)
- [ ] Role acceptance: salary figures hidden from staff without salary visibility (UAT-HR-03)
- [ ] Attendance import for the pay period (UAT-HR-04)
- [ ] OT lifecycle: submit → approve → reconcile 3 h requested / 2 h attended ⇒ 2 h paid (UAT-HR-05)
- [ ] Cash-advance approval — Super-Admin re-authentication + ceiling indicator (UAT-HR-06)
- [ ] Cash-advance rejection with a mandatory reason (UAT-HR-07)
- [ ] Payroll run wizard: blocking flags → calculate → review → guarded approve (UAT-HR-08)
- [ ] Payroll cannot be approved twice (UAT-HR-09)
- [ ] Payslip breakdown correctness + masking for approvers without salary visibility (UAT-HR-10)
- [ ] Tax exports PND.1 / SSO — export job accepted (UAT-HR-11)

> **Bootstrap caveat — read first.** The system ships with a single Super Admin account and
> no other users, roles, or employees. Every scenario below that calls for a limited business
> role (HR officer, payroll approver, "no salary visibility" persona) requires that the Super
> Admin first create that role and a test user for it — that provisioning procedure is
> **UAT-ADMIN-02** in `docs/uat/scripts/06-admin.md` and must be completed before this script.
> All HR master data (employees, OT requests, attendance) is created inside this script.

> **Known gaps surfaced in this script (also listed in the traceability matrix):** OT
> *rejection* has no screen; cash-advance *creation* and *disbursement* have no screens; tax
> exports produce no downloadable file in-app. Scenarios note these inline — do not mark them
> Fail for behaviour the product does not yet offer.

### UAT-HR-01 — HR officer finds their workspace and reads the employee list
- **Business role**: HR officer
- **Business goal**: Confirm the HR workspace opens to a usable employee register.
- **Preconditions / test data**: HR-officer test user exists (UAT-ADMIN-02). At least one employee exists (or run this after UAT-HR-02 and accept an honest "no employees yet" message on a fresh system).
- **Steps**:
  1. Sign in as the HR officer.
  2. Open **HR & Payroll** from the main navigation.
  3. Look over the employee list and its filter controls.
- **Expected result**:
  1. The HR area opens on the **Employees** register.
  2. Each employee row shows code, name, status, employment type, hire date, and base salary; on an empty system a plain "no employees yet" message appears instead.
  3. A status filter lets the officer narrow the list (all statuses / probation / active / resigned / suspended), and a **Create employee** action is available.
- **Acceptance criterion**: An HR officer can reach the employee register and read or filter it without help.
- **Traces to**: UX Acceptance — verified module map (UAT context brief §4, M2): "Employee onboarding — create employee; `EmploymentType` DAILY/MONTHLY, `EmployeeStatus` PROBATION → ACTIVE → RESIGNED/SUSPENDED."
- **Result**: ☐ Pass ☐ Fail ☐ Blocked — Notes / evidence

### UAT-HR-02 — Golden workflow: build the org structure and onboard two employees
- **Business role**: HR officer
- **Business goal**: Set up departments/positions and onboard one monthly-paid and one daily-paid employee, with a base salary recorded for payroll.
- **Preconditions / test data**: HR-officer test user (UAT-ADMIN-02). Fresh org structure preferred.
- **Steps**:
  1. Open **Org structure**. Create department **Production**, then position **Sewing operator** under it. (If you try to create the position first, the system should steer you to create a department first.)
  2. Create a sub-department **Sewing line** with **Production** as its parent.
  3. Back on **Employees**, create employee **Somsri Test** — employment type **Monthly**, hire date today, position Sewing operator. Leave the probation end date blank.
  4. Create a second employee **Somchai Daily** — employment type **Daily**, hire date today, with a probation end date one month in the future.
  5. Open Somsri's record and add a base salary of **15,000** effective today.
- **Expected result**:
  1. The department and position appear in the org tables; **Sewing line** shows **Production** as its parent; a position cannot be saved without a department.
  2. Both employees appear in the register with the correct employment type (Monthly / Daily).
  3. Somsri shows an **Active** status chip. Somchai, having a future probation end date, should read as **Probation** — if the chip reads Active instead, record it in Notes for follow-up (status display for probationers is to be confirmed on the dry run).
  4. Somsri's record shows current salary **15,000.00**; Somchai has no salary yet (this deliberately feeds the "missing salary" flag in UAT-HR-08).
- **Acceptance criterion**: Both employees exist with correct type and status, one with a recorded salary, inside a two-level org structure.
- **Traces to**: UX Acceptance — verified module map (UAT context brief §4, M2): "Base salary required for payroll (flagged 'missing salary')."
- **Result**: ☐ Pass ☐ Fail ☐ Blocked — Notes / evidence

### UAT-HR-03 — Role acceptance: salary figures are hidden from staff without salary visibility
- **Business role**: HR clerk **without** salary visibility (a deliberately restricted persona — see the UAT_PLAN roles table; provision via UAT-ADMIN-02)
- **Business goal**: Prove that a staff member who may manage employee records but is not entitled to pay data can never see a salary figure.
- **Preconditions / test data**: Restricted test user provisioned; Somsri exists with salary 15,000 (UAT-HR-02).
- **Steps**:
  1. Sign in as the restricted clerk and open the employee register.
  2. Look at the base-salary column, then open Somsri's record and check both the profile and the salary section.
  3. Open **Cash advances** and look at the amount on any pending request card (if one exists — see UAT-HR-06 preconditions).
  4. Sign in as the Super Admin and revisit the same screens.
- **Expected result**:
  1. Every money field (salary column, current salary, advance amount) shows a masked placeholder (lock + dots) — never a number, never a blank that shifts the layout.
  2. The employee's national ID is masked under the same rule.
  3. No real figure (e.g. 15,000) is visible anywhere on those screens for the restricted clerk.
  4. The Super Admin sees the real formatted amounts in all the same places.
- **Acceptance criterion**: The restricted clerk cannot read any monetary value on any HR screen; an entitled user sees them normally.
- **Traces to**: BACKEND_SPEC M2 §2.8: "A user lacking `hr.salary.view` gets employee records with all monetary fields omitted."
- **Result**: ☐ Pass ☐ Fail ☐ Blocked — Notes / evidence

### UAT-HR-04 — Attendance import for the pay period
- **Business role**: HR officer
- **Business goal**: Load the month's attendance so OT reconciliation and payroll have real hours to work from.
- **Preconditions / test data**: Employees from UAT-HR-02. An attendance file for the current month in the agreed import format, including — for Somsri — a working day where she stayed **2 hours past normal time** on the date used in UAT-HR-05. **Flagged gap:** the file format is not documented on-screen; obtain the template file from IT before the session.
- **Steps**:
  1. Open **Attendance**; confirm the month grid shows one row per employee with a legend (Present / Absent / Leave / Holiday / No record).
  2. Import the attendance file.
  3. Switch the period to the imported month and review the grid.
- **Expected result**:
  1. A confirmation states how many attendance rows were imported (the count matches the file).
  2. Days with clock-in/out now show **Present**; days with no times show **Absent**; untouched days show **No record**.
- **Acceptance criterion**: The imported month renders in the grid with the row count confirmed and days classified correctly.
- **Traces to**: UX Acceptance — verified module map (UAT context brief §4, M2): attendance import feeding "OT — … RECONCILED (approved = min(requested, attended))".
- **Result**: ☐ Pass ☐ Fail ☐ Blocked — Notes / evidence

### UAT-HR-05 — OT lifecycle: submitted → approved → reconciled (3 h requested, 2 h attended ⇒ 2 h)
- **Business role**: HR officer (submits) and Owner/GM or Super Admin (approves)
- **Business goal**: Approve a 3-hour OT request and prove the company only pays the 2 hours actually worked.
- **Preconditions / test data**: Somsri exists (UAT-HR-02); attendance imported showing she actually stayed 2 hours late on the OT date (UAT-HR-04).
- **Steps**:
  1. On **OT approvals**, raise a new OT request for Somsri: the OT work date, 17:00–20:00 (3 hours), weekday rate (1.5×), reason "Rush order". Submit it for approval.
  2. Confirm the request sits in the approval queue as **Submitted**.
  3. As the approver, open the request, check its details (date, time window, rate, reason), and approve it.
  4. After reconciliation against attendance, check the request's approved hours; then, in the payroll run (UAT-HR-08/10), check the OT line on Somsri's payslip. *Where in the UI reconciliation is triggered is to be confirmed on the dry run — the binding check is the payslip.*
- **Expected result**:
  1. The submitted request shows the 17:00–20:00 window and a **Submitted** status.
  2. After approval it reads **Approved** and leaves the pending queue.
  3. Reconciled/approved hours settle at **2** (the lesser of 3 requested and 2 attended); Somsri's payslip OT line pays **2 hours at 1.5×**, not 3.
- **Acceptance criterion**: The payslip pays exactly 2 OT hours despite a 3-hour request.
- **Traces to**: BACKEND_SPEC M2 §2.8: "OT requested 3h, attendance 2h ⇒ reconcile sets approved_hours=2, pay reflects 2h."
- **Known gap (do not mark Fail)**: There is **no way to reject an OT request in the UI** — only submit, approve, and reconcile exist. Rejection is recorded as Not-UAT-testable in the traceability matrix.
- **Result**: ☐ Pass ☐ Fail ☐ Blocked — Notes / evidence

### UAT-HR-06 — Cash-advance approval requires Super-Admin re-authentication and shows the ceiling
- **Business role**: Super Admin (approves); HR officer for the negative half
- **Business goal**: Approve an employee's cash advance under the company ceiling policy, with the extra authorization step the policy demands.
- **Preconditions / test data**: A **submitted** cash advance for Somsri. **Flagged gap:** there is no screen to raise a cash advance — ask IT to seed one submitted request before the session (record this in Notes).
- **Steps**:
  1. As the HR officer, open **Cash advances** and try the **Approve** action on the request card.
  2. As the Super Admin, open the same card. Read the employee name, amount, reason, and the ceiling indicator.
  3. Choose **Approve**. Read the confirmation dialog's consequence text, enter the Super-Admin password when asked, and confirm.
- **Expected result**:
  1. The HR officer cannot approve — the action is unavailable and explains it needs the Super Admin. (Reject remains available to HR.)
  2. The ceiling indicator states plainly one of: **Within ceiling**, **Approaching ceiling**, or **Over ceiling** (word + symbol, not colour alone), consistent with the policy of 50% of base salary.
  3. Approval is blocked until the password is entered; on confirm, the request is approved and leaves the pending queue.
- **Acceptance criterion**: Only the Super Admin, after re-entering their password, can approve; the ceiling position is visible before they decide.
- **Traces to**: UX Acceptance — verified module map (UAT context brief §4, M2): "**Approve is super-admin re-auth-gated** with a ceiling indicator; **Reject captures a reason**."
- **Known gaps (do not mark Fail)**: **Disbursement has no screen** — on-screen the advance stops at Approved; hand-over of cash is outside the system for now. Also, do not use this scenario to test wrong-password rejection — the password prompt is a deliberate-action safeguard whose server-side check is a known gap (see `docs/testing/test-cases/04-hr.md`, TC-HR-08).
- **Result**: ☐ Pass ☐ Fail ☐ Blocked — Notes / evidence

### UAT-HR-07 — Cash-advance rejection demands a written reason
- **Business role**: HR officer (rejection is not Super-Admin-gated)
- **Business goal**: Decline a cash advance and ensure a reason is always captured.
- **Preconditions / test data**: A second **submitted** cash advance (same seeding note as UAT-HR-06).
- **Steps**:
  1. On the request card choose **Reject**.
  2. Try to confirm with the reason box empty.
  3. Enter reason "Duplicate request" and confirm.
- **Expected result**:
  1. The dialog is visibly a destructive action and states it will reject the employee's request.
  2. Confirmation is blocked while the reason is empty.
  3. With a reason given, the rejection completes and the card leaves the pending queue.
- **Acceptance criterion**: A rejection cannot be recorded without a reason.
- **Traces to**: UX Acceptance — verified module map (UAT context brief §4, M2): "**Reject captures a reason**."
- **Result**: ☐ Pass ☐ Fail ☐ Blocked — Notes / evidence

### UAT-HR-08 — Payroll run wizard: blocking flags → calculate → review → guarded approve
- **Business role**: Payroll approver (Owner/GM or Accountant per UAT_PLAN) — run as Super Admin on the first pass
- **Business goal**: Produce and approve the month's payroll, with the system refusing to calculate while employee data is incomplete.
- **Preconditions / test data**: Somsri (salary 15,000) and Somchai (**no salary** — deliberate, from UAT-HR-02); the approved-and-reconciled OT (UAT-HR-05); attendance imported (UAT-HR-04); ideally the approved cash advance (UAT-HR-06).
- **Steps**:
  1. On **Payroll**, create a run for the current month. The run opens on a four-step wizard: **Inputs → Calculate → Review → Approve**.
  2. On **Inputs**, read the warnings. Somchai should be flagged **Missing salary**; any approved-but-unreconciled OT would be flagged too. Try to continue without resolving anything.
  3. Exclude Somchai from this run, then continue to **Calculate** and run the calculation.
  4. On **Review**, open Somsri's figures and sanity-check the net amount.
  5. Continue to **Approve**; read the summary (number of payslips, net total); choose **Approve payroll**, read the consequence text in the dialog, and confirm.
  6. Reload the page and confirm the run still reads as approved.
- **Expected result**:
  1. The wizard will not let you calculate while a flagged employee is unresolved — the continue action stays blocked and the warning explains why.
  2. After excluding Somchai the warning clears ("ready to calculate") and calculation proceeds; the run's status moves from **Draft** to **Calculated**.
  3. Review lists one payslip per included employee with a net amount in money format.
  4. The approve dialog spells out the consequence (locking the run, pulling outstanding advances into deductions, generating payslips) before you commit.
  5. After confirming, the run reads **Approved** — and still does after a reload.
  6. If an approved advance exists for Somsri, her deductions include a cash-advance repayment (confirm on the dry run — disbursement has no screen, see UAT-HR-06).
- **Acceptance criterion**: Payroll cannot be calculated over incomplete data, and an approved run shows the advance deducted with a net amount exact to the cent.
- **Traces to**: BACKEND_SPEC M2 §2.8: "APPROVED payroll run auto-inserts each employee's outstanding advance into deductions; net exact to the cent; advance outstanding decremented."
- **Result**: ☐ Pass ☐ Fail ☐ Blocked — Notes / evidence

### UAT-HR-09 — A payroll run cannot be approved twice
- **Business role**: Payroll approver / Super Admin
- **Business goal**: Prove the system refuses a duplicate approval of the same run.
- **Preconditions / test data**: The approved run from UAT-HR-08.
- **Steps**:
  1. Re-open the approved run and navigate to the **Approve** step.
  2. Attempt to approve it again (if the wizard still exposes the action).
- **Expected result**:
  1. The second attempt does **not** go through: either the approve action is no longer offered for an approved run, or attempting it produces a clear "already approved" error.
  2. The run's status, payslip count, and net total are unchanged — no duplicate payslips appear.
- **Acceptance criterion**: One run, one approval — a repeat attempt is refused with the state intact.
- **Traces to**: BACKEND_SPEC M2 §2.8: "Approving a payroll run twice ⇒ second call 409." (UI-observable proxy: the "already approved" refusal; the numeric error code itself is backend-level.)
- **Result**: ☐ Pass ☐ Fail ☐ Blocked — Notes / evidence

### UAT-HR-10 — Payslip breakdown is complete for the approver and masked without salary visibility
- **Business role**: Super Admin, then a payroll approver **without** salary visibility (restricted persona per UAT_PLAN; provision via UAT-ADMIN-02)
- **Business goal**: Verify the payslip explains every baht — and that a user not entitled to pay data sees none of it.
- **Preconditions / test data**: The calculated/approved run (UAT-HR-08) with Somsri's payslip, including the 2-hour OT (UAT-HR-05).
- **Steps**:
  1. As the Super Admin, open Somsri's payslip breakdown from the Review step.
  2. Read the lines top to bottom.
  3. Sign in as the restricted approver, open the same run's Review step, and open the same breakdown.
- **Expected result**:
  1. The breakdown shows the pay period and itemises: base salary, **overtime (reflecting the 2 reconciled hours, not 3)**, any allowances; then deductions shown as negatives — social security, withholding tax, cash-advance repayment where applicable — ending in **Net**.
  2. For the restricted approver, net amounts in the review list are masked (lock + dots) and the breakdown reveals no real figures anywhere.
- **Acceptance criterion**: The entitled viewer can reconcile the payslip line-by-line; the restricted viewer cannot read a single real amount.
- **Traces to**: BACKEND_SPEC M2 §2.8: "A user lacking `hr.salary.view` gets employee records with all monetary fields omitted." and "OT requested 3h, attendance 2h ⇒ … pay reflects 2h."
- **Result**: ☐ Pass ☐ Fail ☐ Blocked — Notes / evidence

### UAT-HR-11 — Tax exports PND.1 and SSO: the export job is accepted
- **Business role**: Payroll approver / Accountant (run as Super Admin)
- **Business goal**: Start the statutory PND.1 and SSO export files for an approved payroll month.
- **Preconditions / test data**: The approved payroll month (UAT-HR-08). Background job services running (see `docs/testing/UI_TEST_PLAN.md` §Quickstart).
- **Steps**:
  1. Open **Tax exports**; note the on-screen disclaimer to confirm figures with your accountant.
  2. Set the period to the approved month and start the **PND.1** export.
  3. Start the **SSO** export.
- **Expected result**:
  1. Each export immediately confirms it is being generated and then that the export **has started**, with a note that you will be notified when the file is ready.
  2. No error appears for a valid approved period.
- **Acceptance criterion**: Both export jobs are **accepted** with clear confirmation.
- **Traces to**: UX Acceptance — verified module map (UAT context brief §4, M2): "Tax exports — PND.1 + SSO async jobs (202-accepted; toast only, no download poll)."
- **Known gap (do not mark Fail)**: These exports are **job-acceptance only** — the app currently offers **no download and no "file ready" status** for them. Acceptance stops at the confirmation; the produced file is verified outside the UI. Recorded as such in the traceability matrix.
- **Result**: ☐ Pass ☐ Fail ☐ Blocked — Notes / evidence
